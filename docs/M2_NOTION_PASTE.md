# M2 · 좌우 명령 스냅샷 · 크로스코어 원자성

**브랜치** `fix/m2-command-snapshot` · **베이스** `origin/dev` @ `8498e2f`
**심각도** MEDIUM · **상태** 설계 확정, 구현 대기
**상세 문서** 레포 `docs/M2_COMMAND_SNAPSHOT.md`
**후속 항목 (M2 범위 밖)** 레포 `docs/M2_FOLLOWUP_ITEMS.md`

M2의 범위는 코드 리뷰 지적 ③의 네 항목으로 한정한다. 원자 게시·복사, 임계구역 밖 송신, 한쪽 송신 실패 처리 정의, 안전판정 후 발행. 그 밖의 파생 논의는 후속 항목 문서로 분리했다.

---

## 한 줄로

좌·우 모터 명령이 하나의 결정이 아니라 서로 다른 시점에 따로 읽히고 따로 송신되는 개별 값이다. 제어가 좌우 균형을 맞춰 계산해도 전달 과정에서 그 균형이 깨질 수 있다.

---

## 왜 생기나

두 개의 CPU 코어가 실제로 동시에 돈다. 서로 기다려주는 장치가 명령 경로에 없다.

| 컨텍스트 | 코어 | 주기 | 역할 |
| --- | --- | --- | --- |
| loop / scheduler | core 0 | 10 ms (100 Hz) | 센서·제어·안전판정. state를 쓴다 |
| can_life 태스크 | core 1 | 50 ms (20 Hz) | state를 읽어 EZkontrol 명령 송신 |

기존 코드 주석은 "32비트 float 접근은 word-atomic이라 한 사이클 stale은 무해"라고 적고 있다. 맞는 말이지만 그건 **필드 하나짜리 보장**이다. 필요한 건 좌 전류·우 전류·기어·안전판정을 **묶어서** 같은 순간의 값이라는 보장이고, 그건 어디에도 없다.

## 깨지는 지점 4 + 1

### 1. 좌·우가 다른 tick에서 읽힌다

`can_bus.cpp:164`에서 왼쪽을, `165`에서 오른쪽을 따로 읽는다. 그 사이에 core 0이 `app_wiring.cpp:328-329`를 실행하면 왼쪽은 tick N, 오른쪽은 tick N+1 값이 된다.

- **올라갈 때**: 슬루 리미터가 tick당 10 A로 막아준다. 불일치 최대 10 A. 무해.
- **내려갈 때**: 슬루 제한이 없다. 한 tick에 전체가 0으로 떨어진다. 찢어지면 **불일치 = 명령 전체**.

### 2. send_torque가 공유 기어를 직접, 두 번 읽는다 (가장 나쁨)

`send_torque()`는 전류만 보내는 게 아니라 목표 rpm 부호도 같이 보낸다. D면 +4000, R이면 -4000. 그런데 이 함수는 기어를 **인자로 받지 않고 자기가 전역 state에서 직접 읽는다** (`can_bus.cpp:101`). 그리고 왼쪽용 한 번, 오른쪽용 한 번 호출된다.

경쟁 창이 1번보다 훨씬 넓다. 함수 안의 `twai_transmit(&m, pdMS_TO_TICKS(5))`가 최대 5 ms 블록하므로, 두 번의 기어 읽기가 **나노초가 아니라 최대 5 ms** 떨어져 있다. 제어 주기가 10 ms이니 그 사이에 기어가 바뀔 수 있다.

결과는 **크기 차이가 아니라 방향 차이**다. 왼쪽에 +4000 rpm, 오른쪽에 -4000 rpm.

그리고 이 경로는 **방향 인터록을 우회한다.** 인터록은 정지·스로틀 해제를 확인한 뒤에야 방향을 arm 하고, 그 결과를 `total_torque`의 **부호**에만 적용한다. 반면 CAN 프레임의 목표 rpm 부호는 armed 방향이 아니라 **원시 `state.gear`**에서 오고, 그 읽기는 게이트를 통과한 **이후**에 일어난다. 게이트 통과 시점엔 D였다가 5 ms 뒤 R로 바뀌면, run=true와 구동 전류를 실은 채 목표 rpm만 반대 부호로 나갈 수 있다.

EZkontrol이 토크 모드에서 반대 부호 목표 rpm을 받았을 때의 실제 거동은 **미검증**이다(리뷰 H3). 결과는 "무해한 클램프"부터 "한쪽은 구동, 반대쪽은 제동"까지 폭이 넓다. **검증 안 됐다는 사실 자체가 보내지 말아야 할 이유다.**

한 주기 안에서 기어를 총 세 번 읽는다.

| 위치 | 용도 |
| --- | --- |
| can_bus.cpp:157 | 구동 기어인지 확인 |
| can_bus.cpp:101 (L 호출) | 왼쪽 목표 rpm 부호 |
| can_bus.cpp:101 (R 호출) | 오른쪽 목표 rpm 부호 |

### 3. 한쪽 송신 실패가 무시된다

`send_torque()`가 `twai_transmit()` 반환값을 안 받는다. L은 나가고 R이 실패하면 오른쪽 컨트롤러는 직전 명령을 유지한다. 그런데 `can_commanded_current_L/R` 텔레메트리에는 "둘 다 보냈다"고 기록된다. **로그가 사실과 다르다.** 실패 카운터도 정책도 없다.

버스 부하는 낮으니 큐 포화보다는 error-passive, ACK 없음, bus-off 직전이 현실적 원인이다.

### 4. 안전 판정과 명령 값의 시점이 다르다

태스크 순서가 `drive_supervisor_update` → `safety_task`다. 즉 `state.torque_L/R`은 **그 tick의 안전 판정을 안 거친 값**이다. 유일한 최종 게이트는 life 태스크의 `torque_allowed()` 호출인데, 그 호출과 값 읽기가 분리돼 있다.

두 가지 결과. 최대 한 주기(50 ms) 동안 HALT 이전 명령이 나갈 수 있다. 그리고 로그만으로 "이 명령은 이 판정에 근거해 나갔다"를 말할 수 없다. **사후 추적 불가.**

### 5. 최종 명령 경로에 NaN/Inf 검사가 없다 (검증 중 추가 발견)

`Clamped<LO,HI>::set()`은 NaN을 막지 못한다. NaN과의 비교는 전부 false라 그대로 통과한다. `drive_supervisor.cpp`에는 `isfinite` 검사가 하나도 없다. TV 각 스테이지는 입력을 검사하지만, `drive_supervisor` → `torque_L/R` → CAN 프레임 구간에는 없다.

노션 "반드시 남겨야 할 로직"에 NaN/Inf 검사가 올라 있으나 **실제로는 최종 단계에 존재하지 않는다.** M2에서 같이 넣는다.

## 위험도

한쪽만 전류를 받고 반대쪽이 0일 때 요 모멘트의 이론 상한. 재료는 전부 `realcar_calibration.h`에 있다.

```
500 A × 0.1266 Nm/A  = 63.3 Nm    모터축 토크      MOTOR_KT_NM_PER_A
63.3 Nm × 3.72       = 235.5 Nm   휠축 토크        GEAR_RATIO
235.5 Nm ÷ 0.2387 m  = 987 N      타이어 접지 추력  ROLLING_RADIUS_M
987 N × (1.090/2) m  = 538 Nm     요 모멘트        REAR_TRACK_M
```

이건 상한이다. 타이어가 987 N을 못 전달하면 휠스핀으로 빠지고, 10 kW 규정 제한이 대부분의 속도에서 500 A보다 먼저 걸린다. 36 km/h 부근 10 kW 기준으로 다시 계산하면 한쪽 몰림 시 약 500 N, 요 모멘트 약 270 Nm.

발생 조건이 좋지 않다. 좌우 불일치가 최대가 되는 순간은 **구동 전류를 0으로 끊는 순간**이다. 페달 해제, 브레이크, 피드백 stale/fault, 안전 HALT, 핸드셰이크 손실. 이 순간은 제동 하중 이동으로 리어 그립이 가장 낮은 시점과 겹친다.

발생 확률 자체는 낮다. 다만 재현이 안 되고 로그에도 안 남는 종류라, 확률이 아니라 **결과와 추적 불가능성**으로 우선순위를 매겼다.

## 수정 방향

핵심은 하나. **최종 명령에 필요한 모든 값을 하나의 구조체로 묶어, core 0이 원자적으로 게시하고 core 1이 통째로 복사한다.** 이후 core 1은 복사본만 본다. 1번, 2번, 4번이 같은 수정으로 사라진다.

칠판 비유로는, 칸을 따로 고치지 말고 종이 한 장에 다 적어서 통째로 갈아끼우는 것이다.

### 작업 다섯 덩이

**A. 순수 모듈 신설** — `src/modules/motor_command.{h,cpp}`
최종 명령을 만드는 로직을 하드웨어·전역상태를 모르는 순수 함수로 옮긴다. 입력은 스냅샷과 core 1 소유 게이트, 출력은 좌우 전류·목표 rpm·run 플래그. native 환경이 `src/modules/`를 컴파일하므로 노트북에서 단위 테스트가 된다. LOCKED 파일 변경도 최소로 줄어든다.

**B. 원자 게시·복사** — `portMUX_TYPE` + `portENTER_CRITICAL`
임계구역 안에서는 약 40 byte 구조체 복사만. 수십 ns라 20 Hz 태스크에 영향 없다. **CAN 송신은 반드시 임계구역 밖에서.** `twai_transmit()`이 최대 5 ms 블록하므로 안에 두면 시스템이 멈춘다.
seqlock 같은 락프리 방식은 배리어 하나 빠뜨리면 조용히 깨지고 읽기도 어려워서 쓰지 않는다.

**C. 발행 순서 고정** — 태스크 테이블에서 `safety_task`를 `drive_supervisor_update` **앞**으로.
게시하는 안전 판정이 같은 tick에 갓 갱신된 값이 된다. life 태스크는 `torque_allowed()`를 더 이상 직접 부르지 않고 스냅샷 안의 플래그만 본다. 4번이 구조적으로 사라진다.

**D. 송신 함수에서 전역 접근 제거** — 목표 rpm을 인자로 받는다.
`send_torque()` 안에 `state.`로 시작하는 코드가 하나도 남지 않아야 한다. 2번의 직접 해결. 목표 rpm은 측별로 계산하되 **기어는 복사본에서 한 번만** 읽는다.

**E. 송신 실패 처리** — 반환값을 받아 연속 실패를 센다.
연속 3회 실패하면 해당 측 핸드셰이크를 무효화해서 **기존 재연결 경로**로 흘려보낸다. 새 정책을 만들지 않고 노션의 "한쪽 fault → 양쪽 0 A", "재연결 시 0에서 점진 복원"에 그대로 연결한다.

### 왜 3회(150 ms)인가

"통신 실패 시 양쪽 0"이 오히려 위험해 보일 수 있다. 그런데 **"양쪽을 계속 굴린다"는 선택지가 애초에 없다.** EZkontrol 자체 규칙이 `docs/CAN_PROTOCOL.md`에 있다.

| 신호 | 판정까지 | 결과 | 통제 주체 |
| --- | --- | --- | --- |
| VCU TX 연속 실패 3회 (신규) | 150 ms | 양쪽 0 A | VCU |
| EZkontrol life signal 5회 실패 | 250 ms | MCU 자체 셧다운 + 재핸드셰이크 | 컨트롤러 |
| 컨트롤러 피드백 stale | 250 ms | 양쪽 0 A (기존) | VCU |
| EZkontrol 제어명령 10회 실패 | 500 ms | MCU 셧다운 | 컨트롤러 |

한쪽에 프레임이 도달하지 못하면 **그 컨트롤러는 250 ms 뒤 스스로 꺼진다.** VCU가 뭘 하든 그렇다. VCU가 150 ms에 대칭적으로 끊지 않으면, 250 ms에 한쪽만 꺼지는 비대칭이 **VCU 통제 밖에서** 일어난다. 3회는 컨트롤러보다 먼저 움직이려는 값이다.

또한 0 A는 제동이 아니라 **타력주행**이다. 회생은 `REGEN_HARDWARE_VALIDATED = false`로 꺼져 있어서 0 A는 자유 회전이다. 체감은 스로틀에서 발을 떼는 것과 같고, 좌우 동시라서 요 모멘트를 만들지 않는다.

**컷은 즉시여야 한다.** 도달 불가능한 쪽은 자체 타임아웃까지 직전 명령을 유지한다. 도달 가능한 쪽만 천천히 내리면 **그 시간만큼 좌우 차이가 유지된다.** 즉시 컷이 비대칭 창을 가장 짧게 만든다.

**3은 잠정치다.** 한쪽만 실패할 때 비대칭 지속 시간은 `250 ms - 컷 시점`이라 늦게 끊을수록 짧은데, 이 계산이 "프레임을 놓친 EZkontrol이 자체 타임아웃 전까지 직전 명령을 유지한다"는 미검증 가정 위에 있다. 확정 절차는 후속 항목 문서 1번 참조. **M2의 블로커는 아니다.** 상수 하나이고 `realcar_calibration.h`에서 언제든 바꾼다. 게다가 `twai_transmit()` 실패는 로컬 조건이고 TWAI 주변장치와 버스를 양쪽 ID가 공유하므로 한쪽만 실패하는 경우 자체가 드물다.

**한계 명시.** `twai_transmit()` 성공은 "큐에 넣었다"이지 "컨트롤러가 받았다"가 아니다. 이 검사는 큐 포화·bus-off 같은 로컬 상태만 잡는다. 실제 도달 판정은 기존 피드백 freshness가 한다. 대체가 아니라 더 빠른 보조 신호 하나를 얻는 것이다.

### NaN은 양쪽 동시 차단

한쪽만 0으로 만들면 그 자체가 좌우 비대칭을 만든다. 노션의 "한쪽 컨트롤러 fault 시 양쪽 명령 0 A" 철학과 같게 간다.

## 이 수정으로 해결 안 되는 것

- **좌우 CAN 프레임의 동시 도착.** CAN은 프레임을 직렬로 보내므로 원리적으로 불가능하다. 완화책은 두 프레임을 사이에 아무 작업 없이 연속으로 큐에 넣고 같은 life 바이트를 공유시키는 것뿐이다. **life 바이트 공유는 이미 맞게 돼 있으니 깨뜨리지 말 것.**
- 컴포넌트 테스트 경로의 공유 상태 경쟁 (아래 별건)
- `can_commanded_*`의 역방향 경쟁. core 1이 쓰고 core 0 텔레메트리가 읽는다. 표시 전용이라 무해.

## 별건으로 분리한 발견

**컴포넌트 테스트 상태를 두 코어가 모두 쓴다.**

| 필드 | core 0 | core 1 |
| --- | --- | --- |
| component_test_active | debug_monitor.cpp:86 쓰기 | can_bus.cpp:182,213 쓰기 |
| component_test_normal_inhibit | debug_monitor.cpp:84 쓰기 | can_bus.cpp:150 쓰기 |
| component_test_release_ticks | debug_monitor.cpp:85 쓰기 | can_bus.cpp:146,153 읽기-수정-쓰기 |

`release_ticks`는 core 1의 읽기-수정-쓰기 중간에 core 0이 0으로 덮어쓸 수 있다. 벤치 전용이고 정상 주행에서는 비활성이지만, 올바른 구조는 core 1 소유 상태 기계 + core 0의 일회성 요청 전달이다. 노션의 "Component Test·Time Sync → 시험 전용 빌드" 방향과 함께 처리하는 게 맞다.

## 노션 "반드시 유지" 항목과의 관계

M2는 아래를 **강화**한다. 제거하거나 우회하지 않는다.

| 반드시 유지 항목 | M2에서의 처리 |
| --- | --- |
| 양쪽 handshake 완료 전 토크 금지 | 그대로 유지 |
| CAN stale → 양쪽 0 A | 스냅샷에 담아 일관되게 평가 |
| 한쪽 fault → 양쪽 0 A | TX 연속 실패도 같은 경로로 연결 |
| bus-off → handshake 무효 · 0→램프 복원 | 그대로 유지, TX 실패가 이 경로 재사용 |
| NaN/Inf 검사 + 모터별 상전류 clamp | **신규 추가** (현재 최종 경로에 없음) |
| 센서 오류 → TV만 OFF, 50:50 복귀 | 영향 없음 (TV 상위 단계) |
| 10 kW 규정 전력 제한 | 영향 없음 (drive_supervisor 유지) |
| 브레이크 입력 시 구동토크 차단 | 스냅샷에 brake_active 포함 |
| D/R 전환 정지 + 스로틀 해제 | 스냅샷에 propulsion_direction_armed 포함 |
